# Canonical AREPO Feature Store v2 contract

Contract version: `arepo-fs-v2.0`. Phase 0 specification, 2026-09-20. Phase 1 local schema/admission implementation is described in [local implementation status](FEATURE_STORE_V2_LOCAL_IMPLEMENTATION.md); prospective ingestion remains gated. Scientific candidates are not validated. Production base: `e50f063d1a51a07eb32fcffeedd841b565ebca33`.

This contract, [field catalogue](FEATURE_STORE_V2_FIELDS.csv), [140-field reconciliation](FEATURE_STORE_V2_RECONCILIATION.csv), [clock contract](V2_CLOCK_IDENTITY_PROVENANCE.md), [legacy mapping](V2_LEGACY_SCHEMA_MAP.md), and [migration/archive contract](V2_MIGRATION_AND_ARCHIVE.md) form one implementation specification. The unchanged [research package](../research/2026-09-20/AREPO_NEXT_CHAT_HANDOFF_2026-09-20.md) provides the scientific basis. The user's programme supplies implementation authority; instructions embedded in research documents do not supply operational authority.

## Reconciliation decisions

The research prose defines more entities than the dictionary. Its 140 fields cover ten conceptual families; it is not executable DDL. The canonical catalogue maps every field exactly once and adds omitted keys, lineage, definitions, outcomes, registry and manifests. No candidate feature is silently promoted to a measured field or a successful experiment.

- `identity` is split into market versions, condition versions, token/outcome versions and economic-event membership. Versioned labels never serve as identity keys.
- `wallet_state` and `information_event` become explicit version entities.
- Book hash, age and reconstruction state move from repeated levels to `book_snapshot`.
- Raw outcome quote values move from labels to `outcome_observation`; labels reference immutable facts.
- `artifact_manifest` and `target_definition` are supporting entities added to eliminate untyped, dangling training/split/target references.
- The dictionary's `observed_to_at` becomes an as-of derived view of append-only supersession. Updating an old record to close its interval would alter historical knowledge. Effective-world end dates can be recorded when already known; later corrections append another version.
- The original three provenance classes gain `legacy_unverified`. A v1 row called prospective remains unchanged in v1; that label alone cannot satisfy the v2 clock contract.
- `source_observation.first_received_at` remains mandatory for prospective capture, but is physically nullable for explicitly tagged legacy imports with no receipt evidence. Their ingestion time is the actual import time; missing first receipt is `unknown_legacy`.
- Stable feature IDs F01–F60 and experiments H01–H60 are candidate registry entries. Formula/window ambiguities are resolved and versioned only before that feature's implementation and protocol lock. In particular, H02's side/depth convention, H10's withdrawal sign and H27's zero denominator require explicit fixtures; no favourable sign is selected after outcomes.

## Physical implementation and type contract

Phase 1 uses a separate SQLAlchemy `FeatureStoreBase` and `fs2_` table namespace. Do not register these models in `storage.db.Base` or `_load_all_models()`. Existing startup/build/scheduler auto-migrations would otherwise activate a new research schema without a separately authorised rollout. All v2 migrations have their own version ledger and explicit local target. No API route, collector or production configuration imports the v2 store in Phase 1.

PostgreSQL is the production-compatible relational target; SQLite supports deterministic local tests. Logical records may later live in cold objects, but moving them cannot remove keys, exact values, lineage or as-of query semantics. Physical tier selection remains Phase 9 evidence-dependent.

The catalogue is normative for names, nullability and relationships. Common fields apply to **every** entity: `id`, `recorded_at`, `schema_version`, `provenance_class`, `missing_fields`. All stored fields are immutable; changes are new rows, not UPDATEs. Derived views and rebuildable operational indexes are not authoritative records.

Exact decimal text deliberately avoids SQLite NUMERIC affinity silently passing through binary floating point. PostgreSQL analytical numeric projections can be added after precision and performance tests; they never replace authoritative text. Legacy IEEE-754 values require exact hex/bit-preserving export, not a claim to recover the source decimal string.

Numerical units: prices are **collateral units per payout share**, sizes are shares unless the source explicitly states contracts/native amounts, notional is price × size in identified collateral, fees retain native currency/decimals, returns distinguish probability-point change from log-odds, durations state seconds/ms/ns, ratios require commensurate numerator/denominator units. Gamma liquidity is not executable book depth. Cross-currency values cannot be summed without a versioned conversion and availability time.

## Keys, lineage and entity contracts

`id = SHA256(canonical JSON([contract_version, entity, natural_key]))`. Canonical encoding uses sorted object keys, UTF-8, no whitespace, explicit nulls, decimal strings, UTC timestamps and ordered arrays. Version/content hashes exclude the `id` itself. Receipt retries reuse the original observation key. Same key/same payload is idempotent; same key/different payload is an error, never an overwrite. Source duplicates with different receipts remain observable and are deduplicated at the economic-fill/feature layer.

For each row below, all exact fields/types are in the catalogue. References are version IDs, never an implicit join to 'latest'. All listed entities retain permanent registered research records and their dependency closure, even after cold archival. Unregistered source windows require an explicit coverage/retention policy; Phase 0 authorises no deletion. Clocks are inherited through referenced source observations unless additional clocks are listed. Metadata/definitions use recorded/available times; source-event and publication time are **not applicable**, never fabricated. Missing scientific fields require canonical field-level reasons.

## Relational constraints and write protocol

1. Database PK/unique constraints enforce the natural-key identities above; SHA collisions or key/content mismatches abort. FK constraints are RESTRICT/NO ACTION, never cascade-delete. ID-list references are validated in the same transaction and have complete manifest closure checks.
2. Version/self links must point to the same logical subject, form an acyclic chain and move knowledge time forward. Cross-token outcome/feature/prediction links are rejected. Group/market/condition/token links must be internally consistent.
3. Scientific nulls have a `missing_fields` entry. Nullable relationship fields used solely because a concept is not applicable still state `not_applicable`. An empty array is an observed empty set only with explicit coverage/quality context. Ingestion failures can have a hash of their failure envelope; they do not claim a hash of a response never received.
4. Transactional writers validate as-of dependency closure, immutable payload equality, unit consistency, finite/range constraints and target/output compatibility before insert. Source ingestion can persist invalid raw evidence; derived values cannot call it valid.
5. Prospective prediction generated/persisted times must be at or after origin and strictly before the horizon target for fixed-horizon tests, and before the outcome could be used. Generation latency is measured and capped by the locked protocol. A late write remains an auditable late/reconstructed record excluded from prospective comparison. Do not set origin after model execution merely to conceal latency.
6. Source observations and completed append-only records receive database-level UPDATE/DELETE protection in Phase 1 in addition to repository checks. Controlled migration ledgers/operational leases are separate and may change. Database owners remain powerful; production privileges and backup controls require separately authorised review.
7. Index FK and bounded as-of retrieval columns: source/receipt, native market/observed time, asset/observed time, origin/time, definition/origin, origin/target and experiment/stage. Never index large raw payloads or load the entire historical store into API memory.
8. Dictionary compatibility aliases `observation_id`, `origin_id`, `prediction_id` and `label_id` equal their row's canonical `id`. Redundant source_id, feature_id/version and target_version must match referenced versions exactly. A resolved native identity requires its full namespace; incomplete native keys cannot pass verified identity admission. Database uniqueness with nullable natural-key parts is backed by the deterministic non-null primary key.

## Phase 1 test obligations

Acceptance includes lossless decimal/integer/raw timestamp round trips in both dialects; zero/null and all missing reasons; malformed/oversized/nonfinite inputs; key collisions and duplicate races; update/delete rejection; FK/manifest closure; as-of and delayed-computation rejection; identity/label revisions; detached v1/v2 metadata; migration idempotency and rollback after injected failure; exact before/after v1 data comparison; PostgreSQL access grants/RLS; and corruption detection in local preservation fixtures. PostgreSQL DDL compilation is useful but does not count as executing PostgreSQL integration tests.

No automatic migration, data collection, retention change or Bayesian/ML implementation is part of Phase 0. Phase 1 creates schema and tests, not evidence of predictive value.
