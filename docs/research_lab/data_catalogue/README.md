# Data catalogue

What is archived, under which name, and which test or experiment each file belongs to. The data itself is in the private
GitHub repo `dayyansheikh/arepo-data` as releases (zstd tar parts of the **original bytes**, `files.sha256`, `MANIFEST.sha256`,
`VERIFY.json`). Nothing here is evidence; it is an index. The hashes in a release's `files.sha256` are authoritative.

## Files in this directory

| file | content |
|---|---|
| `README.md` | this page; the release table below is generated by `backend/scripts/archive_catalogue.py` |
| `releases.json` | the same table, machine-readable (one object per release) |
| `<tag>.jsonl` | one row per archived file: `release`, `path` (the path inside the archive and under the repo root), `dir`, `capture_id`, `capture_time_utc` (parsed from the capture folder name such as `20261015T163101Z_ec288b0f`; or from a timestamp in the file name), `date_utc` (day-stamped files such as `trades-20261013.jsonl`), `bytes`, `sha256`, `experiments`, `source` (`host` or `mac`) |
| `RETENTION.md` | what the server may delete after archiving, and the reader changes that make that safe |

Releases with more than 20,000 files (the Mac-era `data-20261011`, `data-20261013-fs2`, `data-20261013-research-lab`) have one row per
capture folder (`granularity: "group"`, `path_prefix`, `n_files`, `listing_sha256`) to keep the catalogue small; their per-file
hashes are in the release's `files.sha256`, which the restore script always uses. Mac-era releases have no per-file byte sizes.

The mapping from directory to experiment is in `backend/astrolabe/research_lab/data_catalogue.py` (`DIR_EXPERIMENTS`). It was derived
from the code that reads or writes each directory, not from file names; the comment above each entry names the readers. A file is
labelled with every experiment whose code reads it (for example every complete snapshot is labelled E002-E007, E011 and FLOW-SCREEN),
so the label means "used by", not "belongs only to".

## Get files back, byte for byte

```bash
# everything one experiment used, from every release (needs gh + zstd; reads the catalogue in this directory)
python3 backend/scripts/restore_from_archive.py --experiment E011 --dest ~/restore_e011
# one snapshot capture
python3 backend/scripts/restore_from_archive.py --tag data-20261015-dsheikh --dest ~/restore \
    --path-glob 'data-dumps/research_lab/snapshots/20261014T163101Z_6e0d303d/*'
# a directory and a time window
python3 backend/scripts/restore_from_archive.py --dir book_sweeps --since 2026-10-12 --until 2026-10-13T12:00 --dest ~/restore
```

The script checks `files.sha256` against `MANIFEST.sha256`, streams the parts from GitHub (each part hashed against the manifest;
the parts are one stream, so a whole release is downloaded even for one file), extracts **only** the selected members into
`--dest` (required; it never writes into a live `data-dumps`), re-hashes every restored file against `files.sha256` and the
catalogue, writes `RESTORE_REPORT_<tag>.json`, and exits non-zero on any mismatch. `--compare-with BASE` also compares each file
with `BASE/<path>` byte for byte. `--list` shows the selection without downloading.
