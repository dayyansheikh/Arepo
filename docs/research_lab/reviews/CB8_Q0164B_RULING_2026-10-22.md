# CB8 q0164b exclusion-keys fix ruling, 2026-10-22 (science-reviewer; saved verbatim)

**Verdict: GO_WITH_CHANGES**

1. **What the composite id means.** `<market>__<other>` is `<successor market_id>__<pred_event_id>` (backend/astrolabe/research_lab/cb4_data.py:2086). The second part is a Gamma event id, not a market id, so taking the market part for the Gamma lookup is correct. But it is incomplete. The same seal has `pred_prices/` and `pred_trades/` files named `<pred_market_id>__<pred_event_id>` (cb4_data.py:2096). That gives 1,922 predecessor market ids, and 574 of them are not among the 1,919 successor markets. CB4 read their prices and trades. The pinned reader only matches `prices|trades/` (cb2_weather.py:660), so these markets never enter the exclusion set. CREATIVE_BATCH_8.md:139-142 says "every market id found in … every committed seal copy". Excluding more is the conservative direction, and the drop happens before the split. Change: the wrapper also adds the `pred_*` market ids, and adds `pred_event_id` straight to the event keys. Count each addition separately.
2. **Seals committed after T_seal.** Including them is acceptable. The rule is "as committed at q0164's start" (CREATIVE_BATCH_8.md:142). q0164b is a new start, and q0166/q0168 re-read every later seal anyway (:149-151). Going back to the T_seal set would mean rebuilding an id set from a run that never wrote one, so don't do that. Two problems remain: **Changes between repeat runs (high).** `exclusion_stage` keys saved batches by their position in `sorted(ids)` (cb6_tail.py:681-705). The id set is read afresh on every one of up to 10 repeat runs. If a seal is committed between runs, saved batches no longer line up with the ids, and nothing warns. Nothing compares the earlier manifest either; `prior` is only checked for the wallet fingerprint (cb8_common.py:373). Change: on the first run, save the pin list and the sha256 of the sorted id set in the run directory. Refuse any later run whose set differs. **The h8 claim is overstated (high, disclose).** h8_text and h8_geo give 0 ids: their seal file lists have no `prices/` or `trades/` entries. The cb11-cb13 holdout seals also give 0. Only h8_tail adds ids (362). Change: record the id count per pin in exclusion_report.json. Label seals that give zero ids "ids not extractable from seal copy". Do not call them covered or disjoint, and say so in the q0164b notes.
3. **Provenance of the wrapper.** A run-scoped wrapper is acceptable, but at present it leaves no lasting record. The `id_normalisation` counts go only into the returned dict, i.e. the queue log. The manifest `params.n_ids` holds the count after normalisation, and exclusion_report.json gives no sign the set was changed. Change: write the sha256 of `cb8_exclusion_fix.py`, the mapping rule and all counts into the run's manifest params or a sidecar listed in the manifest, and copy them into the q0164b notes.

Other defects: (1, medium) Unresolvable ids leave the denominator: `normalise_ids` silently drops them, so they shrink the 2% unverified test instead of counting as missing. Change: refuse if `n_unresolvable_dropped > 0`, or count them in `n_missing`. (2, medium) The job notes describe a different fix ("cb6_tail.lookup_keys_composite … files the row under the original id"); that function does not exist. Rewrite the notes to match the code. (3, medium) q0164's failure record could be overwritten: q0164b reuses the same run id, so its manifest can overwrite q0164's failed manifest. Before running, copy that manifest aside and record its sha256. Keep q0164 recorded as a failed run that exited 0 and was wrongly marked done. (4, low) On the host, confirm whether q0164 left an `exclusion_keys_partial.jsonl`; it failed on batch 0, so it should be empty or absent.

Checked and fine: the 4 new tests pass; `--budget-min` is parsed and not passed twice; the exit-75 logic matches its docstring; the pins in q0164b match q0164 byte for byte; pinned modules are untouched.
Could not verify: host state (q0164 run directory, partial file, pin CSV contents); whether the queue marks a job failed rather than done once `max_runs` runs out without the `until_log_regex` matching; which seals make up the 360-id rise; whether `exclusion_ids_cb8` is itself in the rules hash.
