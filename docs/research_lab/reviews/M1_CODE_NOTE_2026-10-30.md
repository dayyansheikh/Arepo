## Ambiguities (listed, none resolved by a new threshold)
1. First window capture: section 2 says the first possible k has a k - 1 at or after `REGISTERED_UTC`, while E1 only names a missing k - 1. Implemented as class `no_previous_capture`.
2. Event coverage floor (8.3): "0.95 of events" is undefined. Implemented as the event-weighted mean of each event's covered-unit share; "all units covered" and "any unit covered" differ.
3. Capital for non-final units in the `theta_W` and not-found-as-loss lines: no `closedTime` exists, so the 5.2 upper-bound rule (`fetched_utc - t_d`) is applied; a unit absent from the read-out has w = 0 and class `unavailable_fetch`.
4. Thin cells (6): "10 events" counted over the cell's final-state units.
5. Quantiles of `c` (4) and the bid-side carry are over final-state units.
6. Which interval is "wider" (7.1): wider by width of the 95% interval.
7. `fees_enabled` for L1: absent column or empty value is `None`, a non-empty non-truthy text is false (as `population_map_ch251.fee_class`).
8. E3 history counts only status codes proposal or dispute (as J0), not `resolv`-only; look-back includes off-grid retained captures while J0 used on-grid ones.
9. A missing slot is judged 6 h after its grid time, not after a capture start. Captures in the window but off the 2 h grid (tolerance 30 min) are ignored without a count.
10. Duplicate captures of one slot: the earliest start is used (as J0); later ones are counted `duplicate_slot_capture_ignored` in the run log.
11. Slide rule (2): the dates are constants in `SPEC` and are hashed; a slide means editing them in the registration commit before `code_sha` is recorded.
12. Recurring J1 needs a cron entry, not the queue's `repeat` (which re-queues at once). The entry is in `q0751_m1_j1.json` notes and is not added to `crontab.txt`.
13. The text says the analysis keeps units whose `spec_sha` / `code_sha` equal "the pins"; implemented with a pins file given to the analysis, and the running code must equal it too.
14. Contested units' c (8.2) is kept only as per-capture count and sum in `status/` (the mean is a ratio of the sums), since contested units are not written as unit records.
15. S10 week is by capture k's window day from `REGISTERED_UTC`, not by the first data day (J0).
