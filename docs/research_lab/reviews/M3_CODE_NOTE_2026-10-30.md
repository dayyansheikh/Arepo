## 3. Implementation readings of ambiguous text

Marked **(A)** where the reading could really be an amendment to the text and should be ruled by the reviewer or the orchestrator before the freeze; the others are readings
that follow the text or its M1/M2 precedent.

- **R1 (A). Late, duplicate and off-grid capture ids.** 10.2 says they are written to "the next processed capture's write-once status file". Implemented as M1 and M2 did: separate
  write-once files `status/late_<id>.json`, `dup_<id>.json`, `offgrid_<id>.json` (carried by J2's manifest because J2 hashes every status file). Reason: a status file is
  written once, when its capture is processed, so a live pass and a catch-up pass would attach a side fact to different captures, and test (iii) needs identical files. The facts
  and the reasons are the same as the text's; only the container differs.
- **R2 (A). Registration lead enforced in J1.** 12.6 makes a window that started before the registration commit plus 24 h a void; the text requires `registration_commit_utc` in the
  pins file only for the analysis (2.1). `run_pass` also refuses a real pass whose pins lack a parseable `registration_commit_utc`, or whose `REGISTERED_UTC` is less than 24 h after
  it. This is stricter than the text for J1 (it cannot start unregistered); delete `check_registration_lead` if the text should not bind J1.
- **R3. Real J1 refuses while the design text is not frozen.** `SPEC["design_sha256"]` is `None` until the freeze; `check_real_run` refuses a non-dry pass then, and `spec_sha` of a draft
  or dry spec is the sha256 of its canonical JSON. After the freeze one sets `design_sha256` (then `spec_sha` is the design text's sha256, as 2.1 says, and `check_pins` pins the file).
- **R4. `fees_enabled` for L1.** The text passes False "only for a literal served false, otherwise None". "Literal false" is read as the strings `false`, `0`, `0.0`, `f` (case-insensitive),
  the same set as `acc_state`. M2 passed True for a served true; M3 passes None for it (same rate, since True and None behave alike in `costs.taker_rate`).
- **R5. Left-censored first row.** E1 takes precedence: at the first window capture (k - 1 before the window) or after a missing slot, a candidate is counted
  `k_minus_1_before_window` / `no_previous_capture`, not `left_censored_first_row`. Look-back fold captures (never classified) count `left_censored_first_row_pre_window` as a side
  count; classified captures count `left_censored_first_row` with sub-count `in_window`. `no_k_minus_1_row` = a row at an earlier processed capture but none at k - 1.
- **R6. `k_minus_1_not_two_sided` sub-counts.** `one_sided` = exactly one usable value (an ask of 1.0 or a bid of 0 is not usable, so `("0.95", "1.0")` is a one-sided bid),
  `crossed` = both usable and bid >= ask, `unparseable` = neither usable.
- **R7. Near-seen set read.** A market in the near-seen set is skipped in the scan without parsing its prices, so no unit's row after its k enters any count or state. The side counts
  (`crossed_book`, `wide_book_high_ask`) therefore cover only markets not in the near-seen set before the capture (MUST 1 of the re-check). The "in-scope part" of the near-seen set
  (3.3) is counted at entry, from the entry capture's own sidecar row, never re-evaluated later (a later read would be a post-k read for a unit).
- **R8. Event open-member count (S6, S8).** Counted at k over rows with `binary` true, `closed` false, `active` true, including the unit itself; an empty `event_id` is its own
  one-market event (`market:<id>`). This reads, for a ladder, a sibling's row at the sibling's own k; a sibling that is already a unit contributes its row at that capture, which is
  k-visible for the new unit but is post-k content for the older one. Disclosed; nothing for the older unit changes.
- **R9. E7 and E8.** `H_k = end_date_k - t_d` with `t_d` of 3.4 (not the capture start), strict `> 24 h`; age uses the capture's manifest start (`start_k - created_at >= 24 h`);
  `created_at` after `start_k` is `created_at_after_k`. Hours-to-end in the unit is in seconds (`hours_to_end_s`).
- **R10. S4 labels.** `H_k > 24 h` strictly, so the first cell is the open interval (24 h, 3 d) labelled `[1 d, 3 d)` as in the text; a market at exactly 3 d falls in the next cell.
- **R11. Rule ledger tie-break.** Latest visible record by commit time; ties by the later day file, then by position in the ledger (the file's line order as merged). A record without a
  parseable time sorts at the end of its day file's UTC day. The ledger stores `"<class>/<occur_by>"` strings.
- **R12. `rules_gap`.** "Day file merged" = present in the retained directory at a pass that ran the merge; `rules_gap` is tested at classification time against the days in
  [20261020, k's UTC day]. `classed_with_gap` counts every unit with a visible record (including `rules_unresolved`) classified while such a day was unmerged. A day file that appears
  after a unit's pass does not change that unit (units are write-once).
- **R13. Proposal-set recorder.** A market enters capture j's set when its status at the previous processed capture was an empty form (present on that capture), at j it contains a
  whole-token P form, and its row at j maps to scope by j's sidecar. If the previous slot was not processed, the set for j is empty (the transition is unobservable). Written
  for processed window captures only; its status entry carries the sha256 only (not the count).
- **R14. Pre-window manifests that are not complete.** Counted by `discover_all` (`pre_window_manifest_not_complete`) and logged in `logs/j1_runs.jsonl` with the run notes and the merged
  and unmerged `gamma_rules` day counts; they are not in a status file (a count that depends on when the pass runs would break byte identity of status files). Slots with no complete
  capture are `missing_lookback_slot` status files, as in M2.
- **R15. Chain audit.** Every pass audits the status chain (`audit_chain`: consecutive slots, each `state_sha256_before` = the previous `after`, `last_capture_id_before` = the previous
  slot's capture) and requires the state file's sha256 to equal the last status's `state_sha256_after`; one status ahead of the state is accepted (the crash window between writing a status
  and committing the state), a deleted state with more than one status is refused.
- **R16. J0 composition.** `--last-days 8 --lookback-slots 12` as in M2-J0: 12 fold captures plus one k - 1 capture. "Full day" = a UTC day with at least 12 classified captures; rule (a)
  is the median of per-day unit counts over full days (`< 48`); rule (b) is printed as record-only. `candidates_by_category` (all candidates at classified captures by `category_of`) is
  added to give the sports and crypto arm sizes without the order effect of the funnel; it is a k-visible count.
- **R17. Dry-run pad.** The end-of-window state size (ever-seen 600,000, near-seen 150,000, ledger 800,000 records over 250,000 markets) is an assumption, over-stated on purpose;
  the sets are written into `state.json` as sorted JSON lists at every capture.
